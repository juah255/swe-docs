# ORM

ORM stands for **Object-Relational Mapping**. It is a technique where classes or models are mapped to database tables. so developers can work with
data using the programming language instead of writing raw SQL for every
operation.

### What is ORM?

**ORM** (Object Relational Mapping) is a technique
For example, a `users` table may be represented as a `User` model in the
application.

## Why Use an ORM?

ORMs are commonly used to:

- map tables to models or entities;
- perform common `CRUD` operations;
- define relationships between tables;
- manage database migrations;
- handle transactions;
- reduce repetitive SQL; and
- keep database access logic organized.

Common ORM tools include **Prisma**, **TypeORM**, **Sequelize**, **Hibernate**,
**Entity Framework**, and **SQLAlchemy**.

## Basic Mapping

In a relational database:

| Database Concept | ORM Concept              |
|------------------|--------------------------|
| Table            | Model, entity, or class  |
| Row              | Object or instance       |
| Column           | Field or property        |
| Primary key      | Identifier field         |
| Foreign key      | Relationship field       |

Example:

| users table | User model       |
|-------------|------------------|
| `id`        | `user.id`        |
| `name`      | `user.name`      |
| `email`     | `user.email`     |

## Relationships

ORMs usually provide a way to define relationships between models.

### One-to-One

One row in a table is related to one row in another table.

Example:

- one `User` has one `Profile`;
- one `Profile` belongs to one `User`.

### One-to-Many

One row in a table is related to many rows in another table.

Example:

- one `User` has many `Posts`;
- each `Post` belongs to one `User`.

### Many-to-Many

Many rows in one table are related to many rows in another table. This usually
requires a junction table.

Example:

- one `Student` can enroll in many `Courses`;
- one `Course` can have many `Students`;
- an `Enrollments` table connects them.

## Migrations

A migration is a version-controlled change to the database schema.

ORM migrations are commonly used to:

- create tables;
- add, rename, or remove columns;
- define indexes;
- add constraints; and
- update relationships.

Migrations help keep the database schema consistent across local development,
testing, staging, and production environments.

## Transactions

Most ORMs support transactions, which allow multiple database operations to
succeed or fail as one unit.

Example use case:

1. Create an order.
2. Create order items.
3. Decrease product stock.
4. Commit all changes only if every step succeeds.

If any step fails, the transaction should roll back to avoid partial data.

## Query Loading

ORMs often provide different ways to load related data.

### Lazy Loading

Related data is loaded only when it is accessed.

This can be convenient, but it may cause the **N+1 query problem** if many
related records are loaded one by one.

### Eager Loading

Related data is loaded together with the main query.

This can reduce the number of database queries, but loading too much related
data can hurt performance.

## ORM Advantages

- Faster development for common database operations.
- Less repeated SQL in application code.
- Easier model and relationship management.
- Built-in migration support in many frameworks.
- Safer query construction when used correctly.

## ORM Disadvantages

- Generated queries may be inefficient.
- Complex queries can become harder to express.
- Developers may ignore how SQL and indexes actually work.
- Lazy loading can cause hidden performance problems.
- ORM abstractions can make database-specific features harder to use.

## ORM vs Raw SQL

| Use ORM When                              | Use Raw SQL When                         |
|-------------------------------------------|------------------------------------------|
| The query is simple `CRUD`.               | The query is complex or performance-heavy. |
| You need standard model relationships.    | You need precise control over the query. |
| You want migration and schema tooling.    | You need database-specific features.     |
| You want readable application data access. | You are optimizing a slow query path.    |

In real applications, ORM and raw SQL are often used together. The ORM handles
common operations, while raw SQL is used for complex reports, advanced joins,
bulk updates, and performance-critical queries.

## Common Pitfalls

- Not checking the SQL generated by the ORM.
- Creating N+1 queries through lazy loading.
- Fetching more columns or relationships than needed.
- Relying only on ORM validation instead of database constraints.
- Running migrations without reviewing the generated schema changes.
- Ignoring indexes because the ORM hides the database details.

## Summary

An ORM helps application code work with relational databases through models and
objects. It improves productivity and consistency, but it does not remove the
need to understand SQL, relationships, transactions, indexes, and query
performance.

## Mid/Senior Interview Questions and Answers

### 1. What problem does an ORM solve?

**Answer:** An ORM maps database tables and relationships to application models,
reducing repetitive SQL for common CRUD operations and relationship handling.

It improves productivity, but it does not remove the need to understand SQL,
indexes, transactions, and query plans.

### 2. What is the N+1 query problem?

**Answer:** N+1 happens when code loads a list of records and then lazily loads
related data one record at a time. A single endpoint can accidentally issue
hundreds of queries.

Fix it with eager loading, joins, batch loading, dataloaders, or explicit query
design.

### 3. When should raw SQL be preferred over ORM queries?

**Answer:** Use raw SQL for complex reports, performance-critical queries,
bulk operations, database-specific features, and queries that the ORM expresses
poorly.

Keep raw SQL parameterized and tested. It should be an intentional escape hatch,
not scattered string concatenation.

### 4. Why should database constraints still be used with an ORM?

**Answer:** ORM validation can be bypassed by bugs, scripts, concurrent
requests, or other services. Database constraints protect integrity at the final
write boundary.

Use not-null constraints, unique constraints, foreign keys, checks, and
transactions for important invariants.

### 5. What should be reviewed before running ORM migrations in production?

**Answer:** Review generated SQL, locking behavior, data backfill cost, index
creation strategy, rollback plan, and compatibility with currently deployed
application versions.

Destructive schema changes should usually be split across multiple deployments.
